# Post-Incident Review: Checkout Payment Failures (14 March 2026)

_Fictional incident at a fictional company, Lumen Labs._

## Summary

From 09:12 to 10:47 UTC on 14 March 2026 (95 minutes), about **38% of checkout payments
failed** with a timeout error. Roughly 4,100 customers were affected. No payments were
charged twice and no data was lost.

## Timeline (UTC)

- **08:55** — A configuration change reduces the payment service's database connection
  pool from 50 to 5 connections. The change was meant for the staging environment only.
- **09:12** — Payment timeouts begin as the pool is exhausted under morning traffic.
- **09:31** — The on-call engineer, Priya Raman, is paged by the error-rate alert.
- **10:05** — The team identifies the connection pool as the bottleneck.
- **10:38** — The configuration change is reverted.
- **10:47** — Error rates return to normal.

## Root cause

The connection pool size was defined in a shared configuration file used by both staging and
production. A pull request that lowered the value for staging load tests was merged without
noticing that it also applied to production. The alert fired 19 minutes after the problem
began, because its threshold (10% errors over 15 minutes) was too lenient.

## What went well

- Customers' failed payments were never charged, thanks to idempotency keys.
- Status page updates went out every 20 minutes.
